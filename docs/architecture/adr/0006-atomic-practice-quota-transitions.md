# ADR-0006 발음 평가 기회의 원자적 상태 전이와 시간 충전

- 상태: 승인
- 날짜: 2026-07-26
- 관련 Issue: [#38](https://github.com/byeok99/LingKo/issues/38)
- 관련 PR: [#63](https://github.com/byeok99/LingKo/pull/63)

## 배경

평가 요청은 외부 음성 평가 전에 쿼터를 예약하고, 성공하면 사용량으로 확정하며 실패하면 예약을 복구합니다. 기존 구현은 쿼터 행을 조회한 뒤 Java 객체에서 잔여량을 검사하고 값을 변경했기 때문에 동일 사용자 요청이 동시에 실행되면 여러 transaction이 같은 잔여량을 보고 마지막 횟수를 함께 예약할 수 있었습니다.

최초 요청에서는 잠글 쿼터 행 자체가 아직 없어 여러 transaction이 동시에 신규 행을 생성하는 경쟁도 발생했습니다. 외부 평가 호출 동안 DB lock을 유지하면 느린 외부 서비스가 같은 사용자의 다른 요청과 DB connection을 장시간 점유하므로 상태 전이와 외부 호출의 경계도 분리해야 합니다.

2026-08-03부터 자정 초기화 대신 최대 5회, 1시간당 1회 자연 충전을 사용합니다. 기존 물리 테이블과 평가 job의 `quota_date` token은 migration 호환을 위해 보존하지만, 서비스는 사용자별 최신 행 하나를 현재 에너지 상태로 선택합니다.

## 결정

일반적인 예약·확정·복구는 잔여 조건과 값 변경을 하나의 조건부 DB `UPDATE`로 처리합니다.

- 자연 충전 횟수 예약은 `free_used + free_reserved < free_limit`일 때만 `free_reserved`를 증가시키고, timer가 없으면 `next_refill_at`을 서버 시각에서 1시간 뒤로 설정합니다.
- 보상 예약은 `rewarded_reserved < rewarded_available`일 때만 `rewarded_reserved`를 증가시킵니다.
- 확정과 복구는 해당 예약량이 1 이상일 때만 한 번 반영합니다.
- 영향받은 행이 1이면 성공, 0이면 소진 또는 이미 처리된 상태로 판단합니다.
- 마지막 쿼터 예약 충돌은 재시도하지 않고 기존 `QuotaExceededException`과 HTTP 429 계약으로 반환합니다.

현재 에너지 행이 없는 최초 생성만 항상 존재하는 `users` 부모 행에 짧은 `PESSIMISTIC_WRITE` lock을 획득해 직렬화합니다. 부모 lock 획득 후 사용자별 최신 행을 locking read로 다시 확인하고 여전히 없을 때만 생성합니다.

현재 상태 조회와 예약 전에는 최신 행을 잠그고 `next_refill_at` 이후 완료된 1시간 구간 수만큼 `free_used`를 감소시킵니다. 5회에 도달하면 timer를 `NULL`로 만들며 날짜가 바뀌어도 별도 초기화하지 않습니다. 광고 보상은 자연 충전 timer를 수정하지 않습니다.

외부 평가 호출은 예약 transaction이 끝난 뒤 실행합니다. 따라서 Azure 등 외부 서비스 응답을 기다리는 동안 쿼터 또는 사용자 행 lock을 유지하지 않습니다.

## 대안

### 엔티티 조회 후 변경

구현은 단순하지만 여러 transaction이 같은 값을 읽는 lost update 경쟁을 막지 못하므로 제외했습니다.

### 모든 상태 전이에 비관적 lock 사용

정합성은 보장할 수 있지만 같은 사용자의 모든 예약이 순차 대기하고 lock 범위를 잘못 잡으면 외부 호출 시간까지 점유할 위험이 있습니다. 행이 없는 최초 생성에만 부모 lock을 제한하고 일반 상태 전이는 원자 `UPDATE`로 처리했습니다.

### 낙관적 lock과 재시도

`@Version` 충돌을 감지할 수 있지만 예약·확정·복구마다 충돌 예외와 제한 재시도 정책이 필요합니다. 마지막 1회에 대한 경쟁은 기다렸다 재시도해도 대부분 소진 결과이므로 단일 SQL의 영향 행 수로 판정하는 방식보다 복잡합니다.

### MySQL 전용 upsert

`INSERT ... ON DUPLICATE KEY UPDATE`로 최초 생성을 처리할 수 있으나 테스트용 H2와 SQL 이식성이 낮고 생성 직후 현재 transaction의 조회 일관성까지 별도로 다뤄야 합니다. 부모 행 lock 방식은 H2와 MySQL에서 같은 흐름을 검증할 수 있어 선택했습니다.

## 결과

- 남은 무료 횟수 1회에 10개 요청이 동시에 들어와도 정확히 1개만 예약합니다.
- 같은 예약을 동시에 확정하거나 복구해도 상태 전이는 한 번만 반영됩니다.
- 신규 사용자 평가 기회 동시 조회는 현재 행 하나만 생성합니다.
- 정상 예약 경로는 비관적 lock 대기 없이 조건부 `UPDATE` 한 번으로 경쟁을 판정합니다.
- 최초 생성 시 같은 사용자의 다른 사용자 행 lock 작업과 짧게 경합할 수 있습니다.
- 조건부 native SQL은 컬럼명 변경 시 entity refactoring만으로 컴파일 오류를 감지할 수 없으므로 동시성 통합 테스트를 유지해야 합니다.

## 후속 작업

2. Flutter는 광고 전 1회성 server session을 만들고 token을 `customData`로 설정합니다. Backend는 Google SSV 서명, 광고 단위·보상 정책과 provider transaction ID를 검증한 뒤에만 지급합니다.
3. 비정상 종료로 남은 예약을 회수하는 만료 정책을 별도 운영 작업으로 정의합니다.
4. 운영 MySQL 버전 변경 시 `PracticeQuotaConcurrencyTest`를 실제 DB에서 다시 실행합니다.
