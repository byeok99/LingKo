# ADR-0005 통합·릴리스 브랜치 전략

- 상태: 승인
- 날짜: 2026-07-21

## 배경

저장소의 GitHub 기본 브랜치는 `develop`이며 기능, 문서, 운영 변경은 `develop` 대상 PR로 통합하고 있습니다. `main`과 `develop`이 한때 서로 다른 변경을 포함했지만 동기화 작업을 마쳤고, 현재 신규 작업의 기준은 `develop`으로 정리됐습니다.

브랜치 역할을 문서마다 다르게 설명하면 잘못된 base로 PR을 만들거나 출시되지 않은 코드를 `main`에 직접 반영할 수 있으므로 통합과 릴리스 경계를 명시합니다.

## 결정

현재 프로젝트 단계에서는 다음 Git Flow를 사용합니다.

```text
feat/*, fix/*, docs/*, chore/*
              |
              v
          develop
              |
       release PR + 검증
              |
              v
            main
```

- `develop`은 GitHub 기본 브랜치이자 유일한 통합 브랜치입니다.
- 모든 일반 작업 PR은 `develop`을 base로 생성합니다.
- `main`은 배포 가능한 릴리스 커밋만 유지합니다.
- 릴리스는 `develop`에서 `main`으로 PR을 생성하고 릴리스 검증 후 병합합니다.
- `main`에는 일반 기능 커밋을 직접 push하지 않습니다.
- 긴급 수정이 `main`에서 시작된 경우 릴리스 후 같은 변경을 `develop`에 즉시 반영합니다.

## 대안

`main` 하나만 통합·릴리스 브랜치로 사용하는 단순한 trunk 기반 흐름도 검토했습니다. 현재는 개발 중인 변경과 Render·스토어 배포 후보를 분리할 필요가 있고 이미 `develop` 중심 운영이 정착되어 있어 채택하지 않습니다.

프로젝트 규모와 배포 빈도가 바뀌어 분리 비용이 이점보다 커지면 새 ADR로 `main` 단일화 여부를 다시 결정합니다.

## 결과

- 신규 작업과 PR의 기준은 항상 `develop`입니다.
- `main`은 `develop`보다 앞서 기능을 포함하지 않습니다.
- 릴리스 시 `develop → main` PR, 테스트 결과, 마이그레이션, 이미지 태그를 함께 추적해야 합니다.
- GitHub 보호 규칙과 CI는 `develop` PR 검증 및 `main` 릴리스 보호에 맞춰야 합니다.
- 병합된 기능 브랜치는 삭제해 오래된 브랜치를 작업 기준으로 오인하지 않게 합니다.

## 후속 작업

1. `develop`과 `main`에 직접 push 제한과 필수 PR 검증을 설정합니다.
2. CI가 `develop` 대상 PR에서 Backend와 Flutter 검증을 실행하도록 구성합니다.
3. 배포 파이프라인은 `main`의 태그 또는 승인된 릴리스 커밋만 사용합니다.
4. 릴리스 후 `main`과 `develop`의 포함 관계를 확인합니다.
