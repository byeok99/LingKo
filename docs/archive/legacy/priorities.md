# LingKo Priorities

작성 기준: 2026-05-27

이 문서는 LingKo의 현재 우선순위를 별도로 추적하기 위한 문서다.

상세 커밋 단위 작업은 [task-breakdown.md](task-breakdown.md)를 기준으로 관리한다.

## 우선순위 원칙

현재는 기능을 넓히는 단계가 아니라, 핵심 발음 연습 흐름을 실제로 연결하는 단계다.

따라서 우선순위는 다음 기준으로 정한다.

1. 보안과 실행 안정성을 먼저 확보한다.
2. 백엔드 테스트를 복구해 변경 가능한 상태를 만든다.
3. 앱과 백엔드가 같은 API 계약을 보게 만든다.
4. 직접 입력과 추천 문장을 실제 표준 발음 API에 연결한다.
5. 녹음과 실제 발음 평가를 붙인다.
6. 그 뒤에 기록, 로그인, 광고, 코스를 붙인다.

## 전체 우선순위

```text
P0. 보안/설정 정리
P1. 백엔드 테스트 복구
P2. 앱-백엔드 DTO/API 계약 정의
P3. 표준 발음 API 앱 연결
P4. 녹음/발음 평가 API 연결
P5. 추천 문장 서버화
P6. Result 모델 정리와 결과 저장
P7. 조음 가이드 자산 연결
P8. 로그인/기록/광고
P9. 코스 기능 재도입
```

## P0. 보안/설정 정리

목표:

- 저장소에 민감 정보가 남아 있지 않게 한다.
- 백엔드 설정 구조를 일관되게 만든다.
- 로컬/도커/배포 실행 방식이 같은 설정 모델을 쓰게 한다.

왜 먼저 하는가:

- API 키가 노출된 상태에서는 기능 개발보다 폐기/재발급이 우선이다.
- 설정 구조가 맞지 않으면 이후 API 개발과 테스트가 계속 흔들린다.

완료 기준:

- 실제 secret이 추적 파일에 없다.
- `application.example.yaml`과 설정 클래스가 일치한다.
- 로컬 백엔드 실행 절차가 문서화되어 있다.

## P1. 백엔드 테스트 복구

목표:

- 외부 API 키 없이도 기본 테스트가 통과하게 만든다.
- 레거시 테스트와 실제 단위 테스트를 분리한다.

왜 먼저 하는가:

- 현재 백엔드는 좋은 엔진 코드가 있지만 테스트 신뢰도가 낮다.
- 표준 발음 API와 평가 API를 고치려면 회귀 방어선이 필요하다.

완료 기준:

- `./gradlew test`가 통과한다.
- 외부 API 테스트는 별도 profile/tag로 분리된다.
- MVP 문장 예시가 발음 변환 테스트에 포함된다.

## P2. 앱-백엔드 DTO/API 계약 정의

목표:

- Flutter `PracticeSentence`, `PracticeResult`와 백엔드 DTO를 맞춘다.
- 직접 입력, 추천 문장, 결과 화면이 같은 응답 구조를 쓰게 한다.

왜 먼저 하는가:

- API 계약 없이 앱과 백엔드를 따로 만들면 다시 맞추는 비용이 커진다.
- 현재 앱 모델은 이미 UX 기준으로 잡혀 있으므로 이를 서버 계약으로 끌어올리는 편이 빠르다.

완료 기준:

- `prepare` 응답 구조가 문서화된다.
- `evaluate` 응답 구조가 문서화된다.
- 비동기 guide status 정책이 정리된다.

## P3. 표준 발음 API 앱 연결

목표:

- 앱에서 입력한 문장이 실제 백엔드 표준 발음 변환 결과로 표시되게 한다.

왜 먼저 하는가:

- 현재 직접 입력 문장은 더미 `Custom sentence` 값을 사용한다.
- 표준 발음 변환은 이미 백엔드에 있는 가장 안정적인 기능이다.
- 가장 작은 범위로 앱-백엔드 연결을 검증할 수 있다.

완료 기준:

- 앱에서 `맛있겠다.` 입력
- 백엔드가 `마싯게따.` 반환
- 앱 Practice 화면에 실제 결과 표시

## P4. 녹음/발음 평가 API 연결

목표:

- 사용자가 녹음한 파일을 서버로 보내고 실제 Azure 평가 점수를 받는다.

왜 중요한가:

- LingKo의 핵심 가치는 발음 점수와 교정 피드백이다.
- 이 단계가 끝나야 "실제 MVP"라고 부를 수 있다.

완료 기준:

- 앱에서 녹음 가능
- 백엔드 multipart 평가 API 동작
- Result 화면에 실제 점수 표시

## P5. 추천 문장 서버화

목표:

- 홈의 추천 문장을 서버 콘텐츠로 제공한다.

왜 P4 뒤인가:

- 추천 문장은 UX에 중요하지만, 발음 평가가 실제로 동작하는 것이 더 먼저다.
- 초기에는 앱 더미 추천 문장으로도 표준 발음/평가 연결을 검증할 수 있다.

완료 기준:

- 추천 문장 seed 20개 이상
- `GET /api/sentences/recommended`
- Flutter Home에서 서버 데이터 표시

## P6. Result 모델 정리와 결과 저장

목표:

- 더미 결과 화면을 실제 평가 결과 모델로 교체한다.
- 연습 결과를 서버에 저장할 기반을 만든다.

왜 필요한가:

- 현재 `ResultScreen`은 고정 점수와 고정 피드백을 보여준다.
- 실제 평가 API가 붙으면 결과 모델이 반드시 필요하다.

완료 기준:

- Flutter `PracticeResult` 모델 존재
- `ResultScreen`이 실제 API 결과 기반으로 렌더링
- 백엔드 `PracticeSession` 저장 구조 설계 또는 구현

## P7. 조음 가이드 자산 연결

목표:

- 바텀시트의 임시 그림을 실제 입/혀 가이드 자산으로 교체한다.

우선 방식:

- MVP에서는 정적 이미지 또는 사전 생성된 S3 asset 사용
- 비디오 생성은 비동기 job으로 후순위 처리

완료 기준:

- 취약 글자 선택 시 실제 guide URL 기반 이미지 표시
- 로딩 실패 fallback 존재
- guide status 정책 정리

## P8. 로그인/기록/광고

목표:

- 제품 운영에 필요한 계정, 기록, 사용량 제한, 광고 보상을 붙인다.

왜 후순위인가:

- 발음 연습 1회가 실제로 동작하기 전에는 로그인/광고를 붙여도 제품 가치가 검증되지 않는다.

권장 순서:

1. Google OAuth
2. User learning preferences
3. JWT refresh token
4. Practice history
5. Daily quota
6. Rewarded ads
7. Apple Sign in

Apple Sign in은 iOS 배포 준비와 Apple developer 설정이 끝난 뒤 별도 phase로 구현한다. 현재 MVP 인증 기준선은 Google OAuth와 LingKo JWT다.

## P9. 코스 기능 재도입

목표:

- 추천 문장과 직접 입력 흐름이 안정화된 뒤 코스 기반 학습을 붙인다.

왜 마지막인가:

- 코스는 콘텐츠 구조와 진도 저장이 필요하다.
- 현재 MVP에서는 발음 연습 루프 검증이 더 중요하다.

완료 기준:

- Course/CourseSentence/UserCourseProgress 모델 확정
- Home 섹션 또는 하단 Course 탭 중 UX 결정
- 코스 문장 선택 시 기존 Practice 흐름 재사용

## 지금 당장 할 일

가장 가까운 실행 순서는 다음이다.

