# DB 마이그레이션 정책

LingKo는 Flyway를 사용해 MySQL 스키마를 관리합니다.

## 기본 규칙

1. 이미 공유되거나 운영에 적용된 마이그레이션 파일은 수정하지 않습니다.
2. 스키마 변경은 새로운 `V{번호}__설명.sql` 파일로 추가합니다.
3. 엔티티 변경과 마이그레이션을 같은 PR에 포함합니다.
4. 신규 컬럼은 기본값·nullable·기존 데이터 변환을 함께 검토합니다.
5. 인덱스와 유일 제약은 예상 조회·동시성 규칙을 근거로 추가합니다.
6. 삭제·이름 변경은 확장 후 축소 방식으로 단계적으로 진행합니다.

## 권장 절차

```text
1. 새 컬럼/테이블을 호환 가능한 형태로 추가
2. 애플리케이션을 새 구조와 구 구조 모두 읽도록 배포
3. 기존 데이터 backfill
4. 새 구조 사용을 확인
5. 이후 릴리스에서 구 컬럼·코드 제거
```

## 검증

- `./gradlew test`
- 마이그레이션 관련 Repository 테스트
- H2와 MySQL의 문법·제약 차이 확인
- 기존 데이터가 있는 복제 DB에서 사전 실행
- 대용량 테이블 변경 시 잠금 시간 확인

## 롤백

Flyway 적용 후 SQL 파일을 되돌려 쓰지 않습니다. 실패 시 다음 중 하나를 선택합니다.

- 애플리케이션 롤백이 가능한 호환 스키마 유지
- 보정용 신규 마이그레이션 추가
- 데이터 손실 위험이 있으면 백업 복구

## 금지 사항

- 운영 DB에서 `ddl-auto=create`, `create-drop`, `update` 사용
- 수동 스키마 변경 후 마이그레이션 미작성
- 데이터 삭제 쿼리를 백업·검증 없이 적용
- 유일 제약 추가 전 중복 데이터 확인 생략
