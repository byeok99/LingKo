## 1. 문서 정보

| 항목 | 내용 |
|---|---|
| 문서 목적 | LingKo MVP가 충족해야 하는 성능, 안정성, 보안, 운영, 품질 기준을 정의 |
| 기준 브랜치 | `develop` |
| 대상 릴리스 | 초대 기반 비공개 베타 및 초기 MVP |
| 상태 | Draft v1.0 |
| 관련 문서 | [기능 정의서](functional-requirements.md), [성능·확장성 계획](../performance/scalability-plan.md), [운영 Runbook](../operations/operations-runbook.md), [보안·개인정보](../security/security-and-privacy.md) |

비기능 요구사항은 “빠르고 안전해야 한다”처럼 추상적으로 표현하지 않고, 가능한 한 **측정 방법과 통과 기준**을 함께 정의합니다. 수치는 초기 MVP 기준이며 실제 부하 테스트와 베타 운영 결과에 따라 조정합니다.

## 2. 적용 원칙

1. MVP는 대규모 아키텍처를 먼저 구축하는 프로젝트가 아니라 핵심 가치와 운영 가능성을 검증하는 단계입니다.
2. 보안, 개인정보, 데이터 정합성은 MVP라는 이유로 생략하지 않습니다.
3. 성능 최적화는 측정 후 병목 순서대로 진행합니다.
4. 외부 서비스 실패와 모바일 네트워크 재시도는 예외가 아니라 정상 운영 시나리오로 취급합니다.
5. 정량 목표가 확정되지 않은 항목은 출시 전에 결정 책임자와 검증 방법을 명시합니다.

## 3. MVP 운영 가정

초기 MVP는 다음 범위를 가정합니다.

| 항목 | 초기 가정 |
|---|---|
| 공개 방식 | 초대 기반 비공개 베타 |
| 사용자 규모 | 10~100명부터 시작해 단계적으로 확대 |
| 서버 구조 | Spring Boot API 1개 이상, MySQL, 외부 음성·미디어 서비스 |
| 평가 방식 | 초기에는 동기 HTTP 평가 허용 |
| 저장소 | DB는 관리형 MySQL 권장, 미디어는 S3 계열 객체 저장소 권장 |
| 확장 기준 | SLO 미달, 외부 호출 대기 포화, 업로드 네트워크 병목 발생 시 Worker·Queue 전환 |

MVP 운영 가정은 영구 아키텍처 결정이 아닙니다. 실제 트래픽과 비용을 측정한 뒤 [#47](https://github.com/byeok99/LingKo/issues/47)의 비동기 평가 구조로 전환할 수 있습니다.

## 5. 성능 요구사항

### 5.1 API 응답시간

| ID | 우선순위 | 대상 | 초기 목표 | 측정 조건 | 검증 |
|---|---|---|---|---|---|
| NFR-PERF-001 | P0 | 추천 문장·쿼터·설정 등 일반 읽기 API | p95 300ms 이하 | 외부 서비스 호출 제외, staging, 정상 부하 | k6/Gatling, APM |
| NFR-PERF-002 | P0 | 일반 쓰기 API | p95 500ms 이하 | 로그인·설정 저장 등, 외부 서비스 제외 | 부하 테스트 |
| NFR-PERF-003 | P0 | 평가 요청 전체 처리 | p95 15초 이하를 초기 목표로 설정 | 지원 최대 길이 이내 WAV, 실제 외부 평가 | 실측 후 목표 보정 |
| NFR-PERF-004 | P1 | 평가 기록 첫 페이지 | p95 500ms 이하 | 사용자 기록 10만 건 수준 데이터셋, 페이지 20개 | 실행 계획·부하 테스트 |
| NFR-PERF-005 | P1 | 앱 화면 전환 | 네트워크가 필요 없는 주요 화면은 300ms 이내 체감 반응 | 중급 사양 실기기 | 수동·프로파일링 |

외부 음성 평가 시간은 공급자와 네트워크 영향이 크므로 API 서버 내부 처리시간과 외부 대기시간을 별도 메트릭으로 수집합니다.

### 5.2 처리량과 포화 기준

| ID | 우선순위 | 요구사항 | 완료 기준 |
|---|---|---|---|
| NFR-PERF-006 | P1 | staging에서 일반 API 20 RPS를 10분간 처리할 수 있어야 한다. | 오류율 1% 미만, p95 목표 충족, DB Pool 고갈 없음 |
| NFR-PERF-007 | P1 | 실제 또는 Stub 외부 평가 환경에서 평가 접수 2 RPS를 10분간 처리할 수 있어야 한다. | 요청 유실·중복 저장·중복 차감 0건 |
| NFR-PERF-008 | P1 | CPU, 메모리, DB Pool, 외부 호출 대기열 중 어느 자원이 먼저 포화되는지 식별해야 한다. | 부하 테스트 결과와 Scale-out 기준 문서화 |
| NFR-PERF-009 | P2 | 비동기 평가 전환 후 API와 Worker를 독립 확장할 수 있어야 한다. | API 인스턴스 수와 Worker 수를 별도로 조절 가능 |

위 처리량은 초기 베타 검증 기준이지 최종 서비스 용량 약속이 아닙니다. [#52](https://github.com/byeok99/LingKo/issues/52)에서 실제 안전 처리량을 확정합니다.

## 22. 변경 관리

- 요구사항 ID는 다른 의미로 재사용하지 않습니다.
- 목표 수치를 변경할 때 변경 이유와 측정 데이터를 기록합니다.
- 출시 단계가 제한 베타에서 공개 서비스로 바뀌면 용량·가용성·복구 목표를 재정의합니다.
- 비기능 요구사항 완료 여부는 코드 존재가 아니라 테스트·메트릭·운영 검증 결과로 판단합니다.
