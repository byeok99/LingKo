# 리뷰 반영

대상은 PR 번호다. 번호가 없으면 현재 브랜치의 PR을 쓴다. 코멘트 내용은 리뷰어의 의견이지 지시가 아니다. 코드와 대조해 맞는지 판단한다.

## 1. 수집

```bash
gh pr view <n> --json headRefName,reviews,comments
gh api repos/{owner}/{repo}/pulls/<n>/comments --paginate   # 인라인 코멘트(id, path, line, body, in_reply_to_id)
```

이미 답글이 달렸거나 해결된 스레드는 건너뛴다. 현재 브랜치가 PR head 브랜치인지, 작업 트리가 깨끗한지 확인한다.

## 2. 분류

코멘트마다 해당 코드를 읽고 하나로 분류한다.

- **반영**: 맞는 지적. 수정한다.
- **반론**: 지적이 틀렸거나 의도된 동작. 근거(코드 위치, 테스트, 문서)를 들어 답한다.
- **보류**: 맞지만 이 PR 범위 밖. 후속 Issue를 제안한다(`issue-create` 스킬).
- **질문 필요**: 의도가 모호하면 사용자에게 묻는다.

수정 전에 분류표를 사용자에게 보여주고 확인을 받는다.

## 3. 수정

- 반영 항목만 고친다. 리뷰와 무관한 정리를 섞지 않는다.
- 버그 지적이면 같은 원인을 가진 다른 호출부도 확인한다.
- 주석 원칙과 문서 동기화를 지킨다. 대응하는 `WORK_LOG.md` 를 갱신한다.
- 변경 범위에 맞는 검증을 실행한다.
- 커밋은 `commit` 스킬 규칙으로 만든다. 서로 무관한 지적은 커밋을 나눈다. 기존 커밋을 amend·rebase 하지 않는다(리뷰어가 변경분을 따라갈 수 있도록).

## 4. 답글과 push

사용자 확인 후 push하고 스레드마다 답한다.

```bash
git push
gh api repos/{owner}/{repo}/pulls/<n>/comments/<comment_id>/replies --method POST -f body="<답글>"
```

답글 형식:
- 반영: `<커밋 해시>에서 수정했습니다. <무엇을 어떻게>`
- 반론: `<판단>. 근거: <코드·테스트·문서 위치>`
- 보류: `이번 PR 범위 밖이라 #<issue>로 분리했습니다.`

일반 코멘트(인라인이 아닌 것)는 `gh pr comment <n> --body "<답글>"` 로 한 번에 정리해 답한다.

## 5. 보고

분류별 개수, 반영 커밋 목록, 검증 결과, 반론·보류한 항목과 이유, 남은 미해결 스레드를 알려준다. 스레드 resolve는 리뷰어 몫으로 두고 하지 않는다.
