# 트러블슈팅 노트

문제를 수정할 때 영향도와 재사용 가치를 판단해, 같은 작업에서 `docs/private/repository/docs/troubleshooting/`의 노트를 작성하거나 갱신한다. 모든 오류를 문서화하지 않는다.

## 1. 문서화 판단

다음 중 하나 이상이면 후보다.

- API 응답시간, 처리량, CPU, 메모리, DB query 수에 의미 있는 영향을 주는 병목
- N+1, 반복 query, 잘못된 index, 느린 pagination
- memory leak, thread·connection pool 고갈, 파일·socket 미해제
- 동시성, 중복 처리, transaction, lock, cache 불일치로 인한 데이터 정합성 문제
- 사용자 데이터 유실·중복 저장·잘못된 사용자 귀속
- 로그인, token 만료, 권한, 녹음, 업로드, 평가처럼 주요 사용자 흐름을 막는 문제
- 반복 발생하거나 CS로 이어질 가능성이 높은 문제
- 외부 서비스 장애, timeout, retry, Rate Limit
- 배포, migration, 환경변수, Secret, rollback 문제
- 보안·개인정보 문제
- 원인 규명이 복잡하거나 해결 과정을 다른 작업에 재사용할 수 있는 문제

후보면 아래 질문 중 두 개 이상이 `예`일 때 작성한다.

1. 3개월 후 같은 문제를 만났을 때 문서가 도움이 되는가?
2. 다른 개발자가 같은 원인을 다시 조사할 가능성이 있는가?
3. 사용자, 데이터, 비용, 성능 또는 운영에 영향을 주는가?
4. 코드 수정만으로 원인과 예방책이 충분히 드러나지 않는가?

**SEV-1·SEV-2, 보안·개인정보, 데이터 유실 위험은 답변 수와 관계없이 반드시 작성한다.**

## 2. 제외

반복성이나 사용자·운영 영향이 크지 않으면 노트를 만들지 않는다.

- 단순 오탈자, 변수명 수정, IDE 경고
- 원인과 수정이 즉시 명확한 import·compile 오류
- 한 줄 수준의 명백한 null 검사 누락
- 운영 코드에 영향이 없는 테스트 기대값·mock 실수
- 재현되지 않았고 원인도 확인되지 않은 추측
- 기존 노트와 원인·해결책이 같은 문제: 새 파일 대신 기존 노트에 발생 조건, 사례, 증거, 검증 결과를 추가한다.

문서화하지 않기로 했으면 그 판단과 근거를 완료 보고에 한 줄 남긴다.

## 3. 심각도

| 등급 | 기준 |
|---|---|
| SEV-1 | 서비스 사용 불가, 데이터 유실·노출, 광범위한 사용자 영향 |
| SEV-2 | 핵심 기능 실패, 상당수 사용자 영향, 즉시 대응 필요 |
| SEV-3 | 일부 사용자 또는 특정 조건에서 기능·성능 저하 |
| SEV-4 | 영향은 작지만 재발 방지를 위해 기록할 가치가 있음 |

## 4. 작업 절차

1. 수정 전에 `docs/private/repository/docs/troubleshooting/README.md`의 인덱스와 관련 키워드를 검색해 중복 노트를 확인한다.
2. 재현 조건, 로그, query, metric, stack trace 등 증거를 먼저 확보한다. 비밀값과 긴 로그 전문은 제외한다.
3. 임시 조치와 근본 해결을 구분하고, 선택하지 않은 대안과 판단 근거를 기록한다.
4. README의 문서 템플릿으로 `YYYY-MM-DD-<problem-kebab-case>.md`를 작성하고 인덱스에 추가한다.
5. 검증 명령과 실제 결과, rollback 절차, 재발 방지 test·monitoring을 기록한다.
6. 공개 코드·문서에는 필요한 기술 계약만 반영한다. 공개할 사례는 개인 정보와 운영 메모를 뺀 기술 설명만 `docs/engineering/`에 쓴다.
7. 노트 사실 검증과 대응하는 개인 `WORK_LOG.md` 갱신이 끝나야 완료로 본다.

## 작성 원칙

- 측정하지 않은 수치, 확인하지 않은 원인, 재현되지 않은 추측을 사실처럼 쓰지 않는다. 못 잰 값은 `미측정`과 이유를 쓴다.
- 성능 개선은 가능하면 변경 전후 query 수, 응답시간, 메모리, 실행 계획을 같은 조건에서 측정한다.
- 관련 Issue·PR이 있으면 참조한다. 개인 노트를 공개하려고 새 Issue·PR을 만들지 않는다.
- token, Secret, 개인정보, 운영 credential은 기록하지 않는다.
- `docs/private/`가 없는 환경(새 clone)이면 노트를 만들지 말고, 작성할 내용을 완료 보고에 요약해 사용자에게 알린다.
